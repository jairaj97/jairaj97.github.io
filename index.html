THE QUESTION

How does code become a running service?

Build a repeatable path from a source change to a container image and an AKS deployment, with infrastructure and configuration visible in Git.

THE SCOPE

A learning platform, with room to grow.

A hands-on lab for delivery mechanics, documented from the checked-in code. The next iterations focus on health checks, automated validation, and recovery practice.

CONTAINER

Build once, ship the runtime.

The multi-stage Dockerfile restores and publishes with the .NET SDK, then copies the result into an ASP.NET runtime image. The container runs as the app user on port 8080.

Inspect Dockerfile ↗
PIPELINE

Keep the deployed image traceable.

The Build stage pushes both $(Build.BuildId) and latest. The Deploy stage depends on Build and passes the Build ID image to KubernetesManifest@1, overriding the manifest’s default image.

Inspect ci.yml ↗
KUBERNETES

Connect the service to the pod.

The Deployment defines one replica with the label app: devops-demo. A matching LoadBalancer Service maps port 80 to container port 8080.

02 / INFRASTRUCTURE & IDENTITY

Make the dependencies explicit.

Terraform defines a resource group and a Basic-tier ACR with the admin account disabled. A separate AKS resource definition describes the cluster, node pool, networking, and identity settings.

An AcrPull role assignment connects the AKS kubelet identity to the registry. The AKS definition references a different resource group from the new registry; that distinction matters when reviewing the plan.

03 / TRY THE CONTAINER

A small, reproducible starting point.

With Git and Docker installed, run these commands in a terminal. The container listens only on localhost.

LOCAL LABPORT 8080
git clone https://github.com/jairaj97/azure-aks-devops-platform.git
cd azure-aks-devops-platform
docker build -t devops-demo-api:lab .
docker run --rm --name devops-demo -p 127.0.0.1:8080:8080 devops-demo-api:lab

Open http://localhost:8080/health, /ready, or /info. Health and readiness currently return fixed OK responses; they do not test downstream dependencies. View the API ↗

02 / FIELD NOTES

The useful part
of getting it wrong.

Lessons recorded in the project README. Open a note for the symptom, fix, and takeaway.

001DOCKER / BUILD CONTEXTThe dot at the end matters.

What happenedIncomplete COPY instructions and incorrect source paths caused trouble while writing the Dockerfile. The build command also needs a context.

What changedBuild from the repository root and pass . as the context. Make the paths in COPY match the files inside that context.

The takeawayThe Dockerfile describes the build; the context determines which local files the build can access.

002DOCKER / RUN COMMANDRead the command before the container.

What happenedA missing run subcommand and incorrectly used flags prevented the intended container start.

What changedRead the CLI error, correct the command structure, and use an explicit host-to-container port mapping.

The takeawayA CLI invocation error and an application runtime failure are different problems. Identify which layer failed first.

003GIT / LINE ENDINGSMake the repository’s conventions explicit.

What happenedGit reported line-ending warnings while working with the project.

What changedA .gitattributes file was added to keep line-ending behavior consistent.

The takeawayRecord shared file conventions in the repository so they travel with the code.
