BEFORE YOU START

Keep the comparison exact.

Use the same build ID or image tag throughout the investigation. Replace the angle-bracket placeholders with your own names. Confirm your current Kubernetes context and namespace before running commands.

kubectl config current-context
kubectl get deployment -n <namespace>

The examples use Docker, Azure Container Registry, and Kubernetes. They do not change your application Deployment. The ACR connectivity check may create a temporary diagnostic workload. Check application-specific health paths and ports in your manifests.

THE WORKFLOW

01 / BUILD

The image never built.

Start with the first failing build step, not the last summary line in the pipeline.

0 of 3 checks reviewed
CHECK 01

Reproduce with the intended context.

Run from the repository root, or use the same context path as the pipeline.

docker build --progress=plain -t release-check .

Read the result: A missing file in COPY points to path, context, or .dockerignore. A restore or package error is a different build step; inspect that step's input and exit code.

CHECK 02

Compare the Dockerfile path with the build context.

Docker can only copy files made available in the selected context. Inspect the paths referenced in COPY and the ignore file before changing the pipeline.

docker build --progress=plain -f <Dockerfile-path> -t release-check <context-path>

Read the result: If this succeeds with a corrected context, align the pipeline's Dockerfile and context inputs. Do not treat an image push as the cause of a failed local build.

CHECK 03

Confirm the build completed before chasing deployment.

Find the successful build step and the exact tag intended for this run in the pipeline logs. A locally built image proves the Docker build path; it does not prove the registry received the image.

Next handoff: If build succeeds but deployment cannot find or pull the tag, move to Image checks →

02 / IMAGE

The image is missing or cannot be pulled.

Separate a missing tag from authentication and network errors. Pod events give the strongest first clue.

0 of 3 checks reviewed
CHECK 01

Compare the deployed image with the pushed tag.

kubectl get deployment <deployment> -n <namespace> -o jsonpath="{.spec.template.spec.containers[*].image}"
az acr repository show-tags --name <registry> --repository <repository> --output table

Read the result: The full registry, repository, and tag must match. A tag absent from ACR points back to publishing or substitution, even if the Docker build passed.

CHECK 02

Read the Pod's pull event.

kubectl get pods -n <namespace>
kubectl describe pod <pod> -n <namespace>

Read the result: manifest unknown suggests a missing tag; 401 or 403 suggests authorization; timeouts suggest network or DNS. no match for platform points to image architecture.

CHECK 03

Test AKS-to-ACR access when the event points there.

az aks check-acr --resource-group <aks-resource-group> --name <cluster> --acr <registry>.azurecr.io

Read the result: This checks the cluster's ACR access path, not whether a specific image tag exists. Check the kubelet identity's appropriate registry role (AcrPull for a non-ABAC registry) only when authorization is implicated.

If the image pulls and the pod still fails, continue with Rollout checks →

03 / ROLLOUT

The Pod starts but never becomes ready.

Check the rollout, then Pod conditions, events, and application logs.

0 of 3 checks reviewed
CHECK 01

Check what the Deployment is waiting for.

kubectl rollout status deployment/<deployment> -n <namespace> --timeout=180s
kubectl get pods -n <namespace> -o wide

Read the result: A rollout timeout tells you new replicas did not become available in time. It does not identify whether the cause is a crash, probe, image, resource, or scheduling issue.

CHECK 02

Inspect events and probe failures.

kubectl describe pod <pod> -n <namespace>

Read the result: Look for failing readiness or startup probes, restarts, OOM kills, scheduling constraints, and missing configuration. A readiness failure keeps traffic away; a liveness failure can restart the container.

CHECK 03

Read the current or previous container logs.

kubectl logs <pod> -n <namespace>
kubectl logs <pod> -n <namespace> --previous

Read the result: Use --previous after a restart; it may have no logs if the container has not restarted. Compare the app's listen port and health path with the probe configuration before changing thresholds.

If pods are ready but users cannot reach the app, go to Traffic checks →

04 / TRAFFIC

The workload is ready, but the URL fails.

Follow the request from the Service to its ready Pod endpoints before investigating the public edge.

0 of 3 checks reviewed
CHECK 01

Inspect the Service address, selector, and ports.

kubectl get service <service> -n <namespace> -o wide
kubectl describe service <service> -n <namespace>

Read the result: Confirm the selector matches Pod labels, the Service port maps to the app's target port, and an external address exists if this is a LoadBalancer Service.

CHECK 02

See whether the Service has backends.

kubectl get endpointslices -n <namespace> -l kubernetes.io/service-name=<service> -o yaml

Read the result: Missing endpoints, or endpoints with ready: false, direct you back to labels and readiness. Ready endpoints move the investigation to Service ports and the external route.

CHECK 03

Compare an internal path with the public URL.

Run the port-forward command in one terminal, then the curl command in another. Replace the Service port and health path with your manifest's values.

kubectl port-forward service/<service> -n <namespace> 8080:<service-port>
curl --fail http://127.0.0.1:8080/<health-path>

Read the result: If port-forward works but the public address fails, focus on LoadBalancer, ingress, DNS, or network rules. If it fails internally too, revisit Service mapping and the app's response.

After a fix, repeat the failing check and verify the deployed image tag and user-facing health path. A green build alone does not prove the release is serving traffic.
